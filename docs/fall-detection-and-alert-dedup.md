# ربط كشف السقوط ومنع تكرار التنبيهات

## نطاق التغيير

- **الحرارة لم تتغير:** ما زال `SkinTemperatureSensorManager` يولّد `36.5°C` كل ثلاث ثوانٍ، دون تسجيل حساس حرارة فعلي.
- أصبح `AccelerometerSensorManager` يسجّل `Sensor.TYPE_ACCELEROMETER` عند بدء المراقبة، بمعدل `SENSOR_DELAY_GAME`، ويفك التسجيل عند الإيقاف أو تدمير خدمة المراقبة.
- عدم وجود حساس أو فشل التسجيل لا يجعل `FallDetectionEngine` يعتبر نفسه نشطًا.
- يستخدم كشف الصدمة العتبة الموجودة أصلًا: مقدار التسارع أكبر من `25 m/s²`. يتطلب تنبيه جديد عبورًا جديدًا للعتبة، مع مهلة `10` ثوانٍ بين التنبيهات؛ العينات المتتابعة لنفس الصدمة لا تولّد سلسلة تنبيهات. هذه آلية أولية وليست خوارزمية سقوط معتمدة طبيًا، وتحتاج معايرة على الساعة الفعلية.

## هوية التنبيه ومنع التكرار

1. تنشئ الساعة كائن `AlertPayload` واحدًا لكل حدث، بمعرّف UUID وطابع زمني واحد.
2. يستخدم `DataClient` و`MessageClient` نفس المعرّف والطابع الزمني. لا تُعاد صناعة الهوية عند ترميز نسخة النقل الثانية.
3. يمر استقبال القناتين في الجوال عبر `processAlert` نفسه.
4. ينفّذ Room إدخالًا ذريًا بـ `OnConflictStrategy.IGNORE` باستخدام المفتاح الأساسي `id`. فقط الإدخال الجديد يسمح بالإشعار/الإنذار ثم إرسال الرسائل والمكالمات.
5. النسخة المكررة لا تعيد ضبط `isRead` أو `isHandled`. يستمر منع التكرار بعد إعادة فتح التطبيق طالما سجل الحدث موجود في قاعدة البيانات.
6. لا ندمج حدثين منفصلين لأن لهما النص نفسه أو التوقيت نفسه؛ المعيار هو UUID.

لا يلزم ترحيل قاعدة البيانات لأن مخطط الجداول لم يتغير. أما تغيير سلوك الإدخال من `REPLACE` إلى `IGNORE` فيمنع الكتابة فوق سجل تنبيه موجود.

### التوافق والحدود

- يُفضّل تحديث تطبيق الهاتف والساعة معًا. الساعة القديمة ترسل UUID عبر `DataClient` فقط؛ نسختها التي تأتي عبر `MessageClient` بلا معرّف تُتجاهل عمدًا، وتعالج نسخة `DataClient`. لا نصنع معرّفًا جديدًا للرسالة القديمة لأنه يعيد مشكلة التكرار.
- هذا منع لتكرار **محاولة المعالجة**، وليس ضمانًا لوصول SMS أو المكالمة. تبقى صلاحيات Android والاتصال والشريحة مؤثرة.
- ليس تنفيذًا لضمان exactly-once للآثار الخارجية: إذا انتهت العملية بين حفظ السجل وإرسال الرسالة، لن تعيد نسخة مكررة الإرسال تلقائيًا. معالجة ذلك تتطلب سجل مهام إرسال دائمًا وحالات تسليم وإعادة محاولة، خارج نطاق هذا التعديل.
- حذف سجل الحدث أو مسح بيانات التطبيق يزيل ذاكرة منع تكراره.
- لا تتغير سياسات تصنيف النبض/الحرارة في هذا التعديل.

## الاختبارات المضافة

- `FallImpactDetectorTest`: الحدود، المحاور الثلاثة، ارتداد الصدمة، المهلة، القيم غير الصالحة وإعادة البدء.
- `AccelerometerSensorManagerTest`: تسجيل الحساس وإلغاؤه، تمرير أحداثه إلى محرك السقوط، غياب الحساس وتجاهل أحداث ما بعد الإيقاف.
- `AlertPayloadTest`: تطابق هوية الحدث وتوقيته ومحتواه بين القناتين، واستقلال هويات الأحداث المتشابهة.
- `AlertRepositoryTest`: وصول نسخ متزامنة، الحفاظ على علامات القراءة والمعالجة، استمرار المنع بعد إعادة فتح قاعدة البيانات، وقبول أحداث مختلفة بنفس المحتوى.

لتشغيلها في بيئة تحتوي JDK 17 وAndroid SDK 35:

```bash
bash ./gradlew :watch:app:testDebugUnitTest :mobile:app:testDebugUnitTest
bash ./gradlew :watch:app:assembleDebug :mobile:app:assembleDebug
```

**حالة التحقق في هذه الجلسة:** تعذّر تشغيل Gradle لأن Java غير موجودة، وتعذّر تنزيل أدوات البناء بسبب فشل الاتصال بخوادم التنزيل. الاختبارات المضافة لم تُنفّذ هنا. اجتاز التغيير فحص `git diff --check`، وتحققنا من بقاء ملف محاكاة الحرارة مطابقًا للنسخة السابقة. لم تُحدَّث ملفات APK الموجودة في `apks/`.

## تحقق على الأجهزة قبل الاعتماد

باستخدام أجهزة وأرقام اختبار يوافق أصحابها على استقبال التنبيهات، وليس أرقام طوارئ عامة:

1. ثبّت نسختي الهاتف والساعة من البناء الجديد بالتوقيع نفسه.
2. شغّل المراقبة وتحقق من تسجيل التسارع ومن استمرار الحرارة المحاكية عند `36.5°C`.
3. اختبر حدث تسارع اصطناعيًا/مضبوطًا؛ لا تسقط شخصًا أو الجهاز لاختبار الميزة. يجب أن تؤدي سلسلة عينات الصدمة إلى حدث واحد.
4. أرسل SOS مرة واحدة مع توفر القناتين: يجب أن يظهر سجل واحد ومحاولة إرسال واحدة لكل جهة اتصال، ثم يعرض السجل `Ignoring duplicate alert` عند وصول النسخة الأخرى.
5. أرسل SOS مستقلًا ثانيًا: يجب ألا تمنعه هوية الحدث الأول، حتى لو تطابق النص.
6. اختبر وصول القناتين بترتيب عكسي، وإعادة التسليم بعد إعادة تشغيل التطبيق، والإيقاف ثم إعادة بدء المراقبة.
